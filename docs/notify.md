# 报表与推送

对应代码：`autobill/report/`（聚合、图表、模板）、`autobill/notify/`（`mail.py`；以后加 `wecom.py`），以后还有独立的小服务 `relay/`。

**原则：邮件第一眼只看到汇总和可视化；逐笔流水折叠在邮件里（默认收起，轻点展开），完整的[标准账单](statement.md)作为 PDF 附件。** **不做还款提醒**，只展示还款日。

## 统计口径
- **每笔流水**都保留原币种金额（例如澳元消费记为"39.90 AUD，入账 28.25 USD"）。
- **支出合计**：按账单上写的各币种**入账金额**分别相加，再按汇率折算成人民币合计。汇率规则见 [data-model.md](data-model.md#汇率)，报表里注明"按 YYYY-MM-DD 汇率折算"。
- **哪些算支出**：

  | 类型 | 是否算支出 |
  |---|---|
  | `PURCHASE`、`FEE`、`INTEREST`（含分期利息）、`CASH` | 算 |
  | `REFUND`、`REBATE` | 从支出里扣减 |
  | `INSTALLMENT`（分期本金） | **不算**。以农行"总账分期"为例，这笔钱当初消费时已经算过一次，现在只是分期还回去，再算就重复了 |
  | `REPAYMENT`、`FX_TRANSFER`、合成调整 | 不算 |

- **月度归属**：按**交易日所在的自然月**归属，不按账单周期（各行账单日不同）。

### 分类规则
实现在 `autobill/categorize.py`（M6；M7d 加了整词匹配、商户名匹配和行业通用词）。

- **规则文件**：`<数据目录>/rules.yaml`，也可以用环境变量 `AUTOBILL_RULES` 指到别处；`rules.yaml` 不入库。**没有这个文件时用内置默认规则**，内容和仓库里的 [`rules.example.yaml`](../rules.example.yaml) 完全相同（有测试保证两份一致）。
  - 自己的 `rules.yaml` 只写要补的规则。它**排在内置规则前面**：你的关键词先匹配，内置规则照样生效（2026-09-20 起；以前是整个替换，你一写个人规则，内置的品牌词就全失效了）。
- **格式**：`分类: [关键词, 关键词, …]`。关键词有两种：
  - `Woolworths`：描述里任何位置出现就算。连锁品牌名用这种。
  - `word:BAR`：只算完整的单词。匹配 `LS BAR PLANET`，不匹配 `BARBER`；`word:MARKET` 不会误中 `AMAZON MARKETPLACE`。短的通用词用这种。字母和数字算单词的一部分，空格、`*`、`_`、`.` 这些都算分隔。
- **怎么匹配**：拿每笔消费的**原始描述**（`description_raw`）**和解析器拆出来的商户名**一起去匹配，**不分大小写**，分类从上往下，**第一个匹配上的分类生效**。所以容易混淆的分类要放在前面（烟酒、旅行、住宿……），"微信/支付宝（未细分）"放在最后。
  - **不管空格、标点和全角半角**（2026-09-20）：银行把同一家店印成很多样子（`MCDONALD'S`、`MC DONALD S`、`SEVEN-ELEVEN`、`7 ELEVEN`），所以普通关键词只比较字母、数字和汉字（`mcdonalds`）；`word:` 关键词逐个单词比较，这时除字母、数字以外的字符都算分隔，汉字和假名也算（它们之间没有空格）。
  - **银行常把店名截断**（`RESTAURA`、`NOODL`、`WOOLWORT`），所以很多关键词只写前半截。
  - 商户名一起匹配（M7d）：中行把国家代码粘在店名后面（`SUKIYAJPN`），解析器早就把它拆成商户 `SUKIYA` 和地点 `JPN`，但原来只拿原始描述匹配，整词规则对不上。
  - 早先的设计是"先清洗商户名再匹配"。实现时改成了直接匹配原始描述：清洗会去掉"财付通""支付宝-"这些渠道前缀，"微信/支付宝（未细分）"就永远匹配不上了。所以现在是**原始描述加商户名**一起匹配。
- **手续费、利息、取现**不走规则，按交易类型直接归为"手续费""利息""取现"。
- **分类在出报表时现算，不存进数据库**：改了 `rules.yaml`，下一次看报表就生效，不用重新导入。
- **默认规则 = 连锁品牌 + 行业通用词**（M7d）：
  - 只写连锁品牌时，样本里 181 笔消费有 86 笔是"未分类"：大多是悉尼、日本、欧洲的独立小店，每家只出现一两次，按店名写规则永远写不完。
  - 于是每个分类再加上"行业通用词"（`KITCHEN`、`GRILL`、`BUFFET`、`NOODLE`、`word:CAFE`、`word:BAR`、`SUPERMARKET`、`word:MARKET`、`CONVENIENCE`、`AIRPORT`、`STAZIONE`、`TOBACCO`、`CELLARS`……），新加了"烟酒"分类。样本里的未分类从 86 笔降到 37 笔。
  - 每条新词都拿样本逐个核对过；**有歧义的词不放**：`BUTCHER`（"Butchers Buffet"是餐厅）、`METRO`（既可能是地铁也可能是店名）、`HOTEL`（澳洲的 Hotel 大多是酒吧）。宁可留在"未分类"让你补，也不要悄悄分错。
  - 完整内容见 [`rules.example.yaml`](../rules.example.yaml)。
- **扩充默认规则（2026-09-20）**：作者导入历史账单后，816 笔真实消费里有 358 笔"未分类"。
  - 按"先中国大陆和澳洲、再全球主流连锁、再各语言的行业通用词"补规则：中文（餐、菜馆、火锅、奶茶、酒店、航空、旅行社、便利店、药房……）、英文（RESTAUR、STEAK、CHICKEN、TRANSPORT、APARTMENT、CHEMIST……）、日文假名和罗马字（ラーメン、SHOKUDO、KUUKO、DORATSUGU……），以及携程、滴滴、美团、瑞幸、古茗、Chemist Warehouse、Uber、Agoda、Klook、各航空公司等品牌。
  - 新加了三个分类：**旅行**（旅行社、机票、签证）、**购物**（服装、百货、免税店）、**医药**（药房、医院）。"增值服务费"这类银行收的服务费归到"手续费"。
  - 结果：816 笔里未分类的从 358 笔降到 124 笔，逐个商户核对过归类。剩下的大多是只去过一两次的独立小店，交给 [AI 分类](#ai-分类)，或者你自己补 `rules.yaml`。
  - 仍然不放的词：`HOTEL`（澳洲的 Hotel 大多是酒吧，东京迪士尼那类 Resort 也不是住宿）、`METRO`、`SHOP`、`TOTAL`；日本交通卡要写成整词 `word:SUICA`，否则会误中 `MITSUI CARD`。
  - 也考察过 OpenStreetMap 的品牌库（name-suggestion-index，4.8 万个品牌，BSD 许可）：在作者的数据上直接套用，命中的 62 个商户里差不多一半是误判（`HERO OF WATERLOO` 酒吧被当成摩托车修理），真正命中的只占未分类金额的 8% 左右，所以没有整库导入。
- **已知限制**：国内用微信、支付宝付款的消费，账单上只写"财付通，深圳市腾讯计算机系统有限公司"或"支付宝-…"，**看不到真正的商户**。这是银行账单本身的信息不够，不是程序出错。这类消费统一归到"微信/支付宝（未细分）"。
- **为什么不用 MCC（商户类别码）**：MCC 在刷卡授权时就有，但三家银行的电子账单都不打印它（7 份样本全部解码检查过，也没有"商户类别""商户编号"）。按店名反查 MCC 没有免费、可靠的数据库，Visa、Mastercard 的查询接口只对企业开放；而且微信、支付宝付款的 MCC 是支付平台自己的，拿到也分不出真正的店。
- **补规则**：`autobill uncategorised [--cycle 2026-09] [--limit 20]` 按人民币金额列出还没分类的商户（AI 已经分好的不列）（笔数、金额），并生成一段可以直接复制进 `rules.yaml` 的 YAML。你常去的店是固定的，每家只需要补一次。进度邮件的分类卡片下面有"未分类"时也会提示这个命令。

### AI 分类
**原则：解析和金额永远不用 AI**（钱数必须确定、可复查）。**分类可以用 AI**：规则分不出来的商户交给你自己的 AI 接口。2026-09-20 作者决定：AI 的结果**直接生效**，可以**联网搜索**，**不发金额**；这推翻了 M7d 的"AI 建议只打印、不自动生效"。

- **顺序**：你的 `rules.yaml` → 内置规则 → AI 的结果 → 未分类。规则永远优先：AI 分错了，在 `rules.yaml` 里写一行就能改过来。
- **每个商户只问一次**（`autobill/classify.py`）：
  1. 所有新商户一起问（每批 10 个），**不联网**，凭模型自己的知识；
  2. 第 1 步没把握的，**一个一个联网查**：用"店名 + 城市 + 国家"去搜（`ai.web_search`），**默认只搜 1 次**（`ai.max_searches`）：一次查不到就算"不确定"。作者 2026-09-20 定的：为几家难找的小店反复联网，既费 token 又拖慢账单邮件，不值得（实测 98 个商户最多搜 3 次时，一轮要十几分钟、约 1.7 元）。
  - 第 1 步只采用 `high`（很确定）的回答，第 2 步采用 `high` 和 `medium`（网上查到了）的回答。
  - 所有回答都存进 `ai_categories` 表，所以**每个商户只问一次**、报表不会每次都变。
  - **一次没分出来的，直接归"其他"**，不再重试（作者 2026-09-20 定的硬规定：留点冗余，不为少数难找的商户反复花钱）。模型的猜测也存着（`guess`），但不采用；想重问，手动运行 `autobill classify --retry`。"未分类"因此只剩还没轮到问的商户。
- **AI 能看到什么**：每个商户的名字、账单上印的地点（如 `SAPPORO JP`，名字里已经带地点时就不另外给）、付款币种（外币消费给原币种，如 JPY）。地点和币种是为了让它分清同名的店：东京的 "YURI" 和悉尼的 "YURI" 不是同一家。名字发出去前先去掉银行的付款标记（`跨行消费`、`AUSVISA Apple Pay` 这类）：实测模型会把 `AUSVISA`（澳洲 + Visa 卡）读成"澳洲签证"。每个商户带一个编号，模型按编号回答，所以它改写了店名也对得上。**不发**金额、日期、卡号、姓名和账单里的其他内容（有测试检查）。
- **什么时候运行**：
  - `run` / `serve` 每次收完信、发报表之前，自动问新商户（`ai.auto_classify`），每次最多 `ai.per_run` 个（默认 20），剩下的下次再问。
  - 手动：`autobill classify [--limit 50] [--dry-run] [--retry]`，逐个打印分类、把握程度、有没有联网、理由，最后打印用了多少 token 和搜索次数。`--dry-run` 只看不存。
- **出错**：密钥错、余额用完、连不上时，发一封"AI 分类出错"的提醒（同一个问题只发一次，恢复后自动清除）。这时新商户先算"未分类"，账单和报表照常。
  - 只是某个商户的回答不合格（没按格式回答、太长被截断）时不算出错：一批里的先对半拆开重问，单个商户就算"不确定"，其余照常继续（实测 98 个商户里遇到过这两种情况）。
- **邮件里的标记**：逐笔流水里，AI 分的类后面带"（AI）"，比如"餐饮（AI）"；AI 没分出来的是"其他（AI）"。
- **提供方**（`autobill/ai_anthropic.py`，`config.yaml` 的 `ai.provider`）：
  - `deepseek`：DeepSeek 的 Anthropic 兼容接口 `https://api.deepseek.com/anthropic`，默认模型 `deepseek-v4-flash`。**联网搜索由 DeepSeek 在它那边完成**（`web_search` 服务端工具），所以一个 DeepSeek 密钥就够，不用另外接搜索服务。
  - `anthropic`：同一套代码，接任何说 Anthropic Messages 格式的接口，在 `ai.base_url`、`ai.model` 里指定（没有默认模型，必须写）。
  - 密钥只从环境变量 `AUTOBILL_AI_API_KEY` 读（服务器上写在 `autobill.env`）。
  - 以后要接别的（比如 OpenAI 兼容格式、本机 Ollama），写一个提供方并 `register`，别处不用改。
- 没配置 `ai.provider` 时一切照旧：不问 AI，`classify` 命令提示一句。

#### 把 AI 的结论沉淀成规则
2026-09-20 作者决定。`ai_categories` 只存在服务器的数据库里，而规则在这个公开仓库里。所以把 AI 分对的商户**写成关键词规则**，一举三得：进了 Git 就有备份、规则的优先级高于 AI 答案（AI 以后抽风也盖不过它）、别人拿到的默认规则也更全。

用 `scripts/export_ai_categories.py` 导出，**只读**（`mode=ro` 打开数据库，写不进去），`serve` 在跑也能用；只用标准库，服务器上 `python3` 直接跑，不用进容器。脚本在源码 checkout 里，数据库在 compose.yaml 旁边，所以两个路径都要写全：

```bash
python3 ~/autobill/scripts/export_ai_categories.py ~/autobill-docker/data/autobill.db            # 表格，先看一眼
python3 ~/autobill/scripts/export_ai_categories.py ~/autobill-docker/data/autobill.db --yaml     # 可以粘的 YAML
python3 ~/autobill/scripts/export_ai_categories.py ~/autobill-docker/data/autobill.db --review   # 要你自己判断的那些
```

- **为什么不能整表导出**：`ai_categories.merchant` 存的是解析器拆出来的商户名，**解析器认不出商户时存的是原始描述**（见 `autobill/classify.py`）。微信、支付宝付给个人的消费，描述里带着收款人的真名，而 [tests/fixtures/README.md](../tests/fixtures/README.md) 定了别人的真实姓名也不公开。
- **分成三档**（`verdict_for()` 判一次原名、判一次清理后的名字，取更严的那个）：
  | 档 | 判断依据 | 默认打印？ |
  |---|---|---|
  | 保留在服务器 | 名字里有"财付通/支付宝/微信/转账/代付/收款/汇款/个人"，或者没有任何流水用这个商户名 | 不打印，`--show-held` 才列 |
  | 要你自己判断 | 整个名字就是两三个汉字（可能是连锁店如古茗、海底捞，也可能是人名），或者名字带汉字**且**和某条流水的原始描述一模一样 | 不打印，`--review` 才列 |
  | 可公开 | 其余的 | 打印 |
- **每道检查各自能做到什么**（三档只值这几条检查的分量，所以写清楚）：
  - **真正挡住人名的是支付渠道关键词**。国内微信、支付宝付给个人，描述里必然带渠道词，人名跟着一起被扣下。
  - "没有流水用这个商户名"**只能抓到 `transactions.merchant` 为空的行**。作者的数据里 1807 笔有 195 笔把整条描述存进了 `merchant`，这些行这道检查不触发——所以才有上面那条"带汉字且整条就是原始描述"的兜底。
  - 两道检查都**认不出拉丁字母写的人名**（比如用自己名字开店的个体户）。所以**粘之前要扫一眼**，像人名的不要放。
- 判断"是不是整条原始描述"用的是**清理后**的名字：`跨行消费`、`境外消费` 这类是银行自己的前缀，不是店名的一部分，而且几乎每笔境外消费都带，按原名判会把绝大多数行都推进"待判断"。
- **默认输出是按"宁可少放"过滤过的，但不是免检**：扣错一个商户只是少一条规则，放错一个名字就进了公开历史，拿不回来。`--review` 和 `--show-held` 的输出只在服务器上看。
- **名字会先清理再导出**（`clean_name()`，和 `suggest.py` 的 `shown_name()` 同样两条正则）：去掉 `跨行消费` 这类前缀和 `AUSVISA Apple Pay` 这类付款标记，**同一家店的多种写法合并成一条规则**，注释里标"覆盖 N 种写法"。不然 FAROS BROS 会因为写法不同出现三次，而且每条只能命中那一笔。
- 清理后**仍带四位以上数字的不自动截断**，只在注释里标"建议改短"：`TOTAL 4375372` 截成 `TOTAL` 反而会造出项目明令不放的歧义词，这种取舍只能你自己做。
- AI 没把握的（`category IS NULL`）一律不导出：那不是分类结论，按"其他"算。
- 只导出商户名、地点、币种和把握程度四样，**不导出**金额、日期、卡号、模型名、询问时间和 AI 给的理由（有测试检查）。
- 合并时**两份规则文件要一起改**：`rules.example.yaml` 和 `src/autobill/default_rules.yaml` 必须完全一致，`tests/test_categorize.py` 会检查。逐条核对，可以把店名改短或换成通用词；**有歧义的词不要放**（见上面"仍然不放的词"）。
- 过滤器本身有测试（`tests/test_export_ai_categories.py`）：和 `scripts/check_identity.py` 一样，**先证明它扣得住人名，才能相信它说的"可公开"**。

作者自己的 `rules.yaml` 被 `.gitignore` 排除、目前没有备份，而它比 AI 分类更难重建（数据库丢了能重新解析，AI 分类丢了能重新问，手攒的规则只能重攒）。想备份就把它的内容合并进上面那两份文件，个人专用的几条留在本地。

## 账单月邮件
**没有定时月报。一个账单月收齐之后，发一封**（2026-09-20 改；M7c 原本是每来一张卡的账单就发一封进度邮件）。

**为什么改**：作者 6 张卡的账单日错开在 2、3、11、17、24 号，几乎每张卡单独一天到，所以原来一个月要收 4~5 封。而**邮件投递之后改不了**（IMAP 里"替换"= 删 + 写，要动邮箱写权限，和"程序只读邮箱"的红线冲突），于是 AI 补完分类、`reparse` 修正金额之后，先发的那几封永远停在过时的状态。作者的选择是：宁可只发最终版一封。代价是月初到月底之间收不到邮件；想中途看，用下面的 `resend`。

- **账单月 = 出账日所在的月份**，和银行的叫法一致（银行的"2026年09月账单"就是 9 月出账的那一期）。每张卡每月出账一次，所以一个账单月里每张卡最多一份。
- **卡包**：`config.yaml` 的 `cards.portfolio` 列出每月应该出账的卡和大约的账单日（见 [config.example.yaml](../config.example.yaml)）。
  - 不配置时，最近约两个月出过账单的卡算"应有"，账单日取它最近一期的日子。
  - 配了卡包也不会把"那时还没开卡"的卡算进过去的月份：某张卡的第一份账单比这个月还晚，就不列。
- **每张卡的状态**：
  - **已出账**：这个月有它的账单，显示应还（折合人民币）、出账日、还款日；
  - **待出账**：还没到，而且没超过通常账单日 7 天。只要还有卡是这个状态，这个月就不发邮件；
  - **可能无账单**：超过通常账单日 7 天还没到。有的银行在没有消费的月份不出账单，这样就不会一直卡在 5/6。
- **什么时候发**：
  - **这个月收齐才发**：每张应有的卡要么已出账，要么超过通常账单日 7 天变成"可能无账单"。没收齐就一封都不发，这个月的账单先攒着（`reported_at` 仍为空），下一轮再看。
  - 收齐那一轮发**一封**，覆盖这个月全部卡；不同账单月各发一封，从早到晚。
  - **最晚什么时候到**：最慢那张卡的通常账单日 + 7 天。作者的卡最迟 24 号，所以最坏情况是月底前。
  - 收齐之后又来了迟到的账单，**会再发一封**（那是新消息，不是重复）。
  - 判断"收齐"用的是 `cycle_complete()`（`report/cycle.py`），它只查哪些账户这个月出过账，不加载账单、不渲染报表——邮件要等到收齐才建，否则未收齐的那几周每半小时白渲染一次。它和报表自己的 `CycleReport.complete` 必须同一口径，有测试钉住。
- **想中途看，或者修好之后要最新版**：`autobill resend --cycle 2026-08`
  - 按**现在**的账单、分类、汇率重算一封发出来，并进同一个对话；
  - `reparse` 修正了金额、AI 补了分类之后都用得上（`reparse` 本身不会重发，见 [pipeline.md](pipeline.md#cli)）；
  - **不改账单的已发送状态**，只把新邮件的 Message-ID 追加进 `cycle_threads`；
  - 不带"新账单"区块（这是刷新，不是新账单到账）。
- **邮件折叠成一个对话**：同一账单月的邮件用同一个主题 `📊 2026年9月 信用卡账单`，第二封起（迟到的账单、`resend`）带 `In-Reply-To` / `References` 指向之前的邮件（记在 `cycle_threads` 表里）。Apple 邮件按这两个邮件头把它们折叠在一起，比只靠主题相同可靠。**每封都是当场从数据库重算的整月完整视图**（分类不存库，见[分类规则](#分类规则)），所以同一个对话里永远以最后一封为准。
- 想随时查看某个自然月的汇总，可以在终端运行 `autobill report --month YYYY-MM`（按交易日归属，见上面的统计口径）：
  - 每张卡、每份账单、每个币种一行支出合计，以及所用汇率和折算后的人民币；
  - 分类（返现、退款单独一行"扣减"）、按卡、近 6 个月、支出最多的商户、未分类的商户；
  - 每笔金额按它所属账单的汇率折算；各项分别四舍五入，和合计可能差几分钱。

## 每月备份
**每月那封邮件带一份数据库备份**（2026-09-20 作者要求"出账单了备份一次"）。实现在 `autobill/backup.py`。

- **为什么**：数据库是这里唯一重建不出来的东西——账单能从 `raw/` 重新解析，AI 分类能重新问，但前提是这个文件还在。服务器是 Oracle 免费机，说没就没。
- **怎么带**：压缩后附在邮件里（490 KB 的库压成约 120 KB，iCloud 单封限 20 MB，毫无压力）。**你的邮箱就是异地备份**：服务器整个没了，最新那封月度邮件里也有全量数据。
- **服务器上也留一份**：`data/backups/autobill-2026-10.db.gz`，默认保留最近 6 个月（`backup.keep`）。
- **用 SQLite 自己的备份接口，不是复制文件**：数据库是 WAL 模式，最新的改动还在 `autobill.db-wal` 里，直接 `cp autobill.db` 会丢（2026-09-20 手动备份时真踩过一次，有测试钉住）。
- **只在自动发的月度邮件里带**，`resend` 重发不带（否则你每看一次就多一份重复附件）。
- 备份是在生成邮件时取的，所以里面还不知道"这个月已经发过报表"。**还原之后那个月的邮件会再发一封**——无害，总比反过来好。
- **备份失败不挡报表**：比如服务器上的 `backups/` 没有写权限，月度邮件照常发出（能附上的话照样带附件），日志里多一行"数据库备份失败……"。
- 不想要：`config.yaml` 写 `backup: {enabled: false}`。
- **`raw/` 那 25 MB 原始邮件不备份**：它们本来就还在你的 iCloud 邮箱里，真丢了重新拉一遍即可。
- **怎么还原**：见 [deploy.md](deploy.md#从备份还原)。

## 邮件内容
**只为 iPhone 上的苹果邮件（iCloud 邮箱）排版，目标是 iOS 原生 App 的质感**（2026-09-19 作者要求：完全抛弃财务报表的表格感）。苹果邮件用 WebKit 内核，是所有邮件客户端里 CSS 支持最好的，所以这里**只优化它一个**，不为别的客户端做兼容（2026-09-20 作者确认）。

**设计参考**：
- **Apple 自己的设计语言**（Human Interface Guidelines）：大标题、分组圆角列表和缩进的细分隔线（设置、钱包）、系统配色（分组背景 `#F2F2F7`，深色是纯黑 + `#1C1C1E`）、`-apple-system` 字体和 SF Pro Rounded 大数字；
- **钱包 App**：卡片缩略图（深灰渐变，只有银行首字和尾号，不仿冒银行卡面）；
- **屏幕使用时间**："比上个月 +12%"的环比写法；
- **Apple Card、Copilot Money**：金额的"大整数、小分位"写法；每个分类一个 emoji 图块；圆盘图 + 图例；Apple Card 的月度活动柱状图（近 6 个月趋势）。

**一封邮件就是这个月的完整报告**（2026-09-20 重做，替换了原来"每来一张卡发一封进度邮件"的版式）。**第一眼只看到汇总**，逐笔流水折叠起来。从上到下：

1. **大标题** `2026年9月`，下面一行 `✓ 本月账单已齐`（有超时的卡时补"，N 张可能无账单"）。
2. **大数字**：本月合计应还（折合人民币）+ 一行小字"N 张卡的账单"。
3. **卡片**：分组列表，每张卡一行：钱包式缩略图、银行和尾号、**出账日和还款日**、右边是应还和状态（✓ 已出账 / 时钟 待出账 / ! 可能无账单，图标加文字，不只靠颜色）。
   - **外币卡在人民币下面再给一行原币种**（`US$168.50`）：折算是给你看总额的，真正要还给银行的是那个币种的数（2026-09-20 作者要求）。
4. **本月消费**：**圆盘图**（donut，中间是消费合计）+ 环比小药丸 `比 8 月 +12%`；下面每个分类一行（emoji 图块、颜色标记、占比、金额）。
   - 颜色：前 4 个分类用验证过的分类色（第 1–4 号），其余合并成"其他"（灰色），"未分类"放最后（更淡的灰）。这一组颜色用 dataviz 的校验脚本在浅色、深色两种背景下都跑过。
   - **图例必须带占比和金额**：占比 2% 以下的切片在图上几乎看不见，数字不能只存在于图里。
   - **和平时比**（2026-09-24 作者要求，参考 Copilot Money、Monarch）：明显偏离平时的分类，在名字下面加一行灰色小字 `比平时多 ¥800` / `比平时少 ¥400`，底部说明补一句"平时指前 3 个月的中位数"。
     - **平时** = 这个月之前 3 个账单月里、有账单的那几个月，这个分类金额的**中位数**：某个月买了机票也拉不动它。有账单的月份不到 2 个就不比。
     - **两个条件都满足才标**：差额至少 ¥300，而且至少 30%（小分类的零碎波动和大分类的正常浮动都不标）；多了少了都标；**最多 3 个**，差额大的在前。
     - 只标有名字的前 4 个分类行；"其他"和"未分类"是兜底，不比。
     - 用灰色，不用红绿：多花不一定是坏事（出去玩了一趟），只展示，不评判。
     - 分类是出报表时按当前规则现算的，历史月份也按同一套规则归类，所以改了规则不会造成假的"变化"。
     - 常量在 `report/cycle.py` 开头（`BASELINE_MONTHS`、`NOTE_MIN_DIFF`、`NOTE_MIN_RATIO`、`NOTE_MAX`）。
5. **近 6 个月**（2026-09-24 作者要求）：每个账单月一根柱子，**本月用强调色，前 5 个月用灰色**，只在本月那根上写金额；下面一行"N 个月平均 ¥X · 本月比平均多/少 N%"（平均是图上有账单的那几个月，含本月）。
   - 口径和"本月消费"完全一样（扣掉返现和退款、外币折人民币），所以本月那根就是上面圆盘中间的数；以前的月份按当月账单各自的汇率折算。
   - 某个月一张账单都没有，那个位置写"—"，不跳过，时间轴保持均匀；花了 ¥0 的月份只有底线，没有柱子。
   - 有账单的月份不到 2 个时整块不显示（一根柱子没有可比的）。
   - 颜色：强调色和灰色（`--other`，`#8E8E93`）这一对用 dataviz 校验脚本在浅色、深色下都跑过：色觉障碍和正常视力下都分得开，对背景的对比度都够 3:1。
   - 每个月的金额都写在图的 `aria-label` 和纯文本版本里，不只存在于柱子的高度里。
6. **花得最多的商户**：同样是圆盘图，中间写前 5 名占本月消费的比例，下面五行明细。
7. **全部流水**：**所有卡合在一张表里**，按日期分组，默认**折叠**，轻点展开。每笔一行：
   - emoji 图块、商户、小字（卡 · 分类 · 地点 · 分期 · 入账日）；
   - 右边**以消费当地的币种为主**（`JP¥12,345`，日元和人民币都用 ¥，所以日元写成 `JP¥`），下面小字给折算的人民币 `≈¥612`；本币消费不重复显示人民币；
   - 返现、退款显示成绿色的 `+`；还款、分期本金、购汇、调整标"不计入支出"。
8. 页脚：汇率说明、"金额以银行原账单为准"、生成时间。

**不再有**：进度圆环（收齐才发，圆环永远是满的）、"新账单"区块、日历式还款日一览（还款日已经在卡片那一行）、PDF 附件（2026-09-19 就决定原始账单在邮箱里看）、**每日消费柱状图和"最大的一笔"**（2026-09-24 作者决定删掉：各张卡的账单周期错开，合在一起画的每日图两头只算到部分卡，日均也被拉低；最大的一笔经常和商户排行第一名重复。标准账单里一张卡一个完整周期，每日图保留）。

**实现**：`autobill/report/cycle.py` + 模板 `report/templates/cycle_report.html.j2`；共用的配色、emoji、货币符号在 `report/style.py`。

- **折叠用 CSS 的"复选框技巧"**（checkbox hack），不用脚本：一个隐藏的 `<input type="checkbox">`，点它的 `<label>` 切换选中状态，CSS 用 `:checked` 显示或隐藏**紧邻**的 `.panel`。靠相邻选择器，所以这三个标签的顺序不能动。
- **圆盘图是内嵌 SVG**（`donut_svg()`）：和进度圆环同样的画法（`stroke-dasharray` 画弧），切片之间留 2px 间隙，颜色用 CSS 类，跟随深色模式，`aria-label` 里写全每个切片的名字和占比。
- **苹果邮件的处理**：
  - `<style>`、CSS 变量、`prefers-color-scheme` 深色模式、内嵌 SVG 都能用，所以没有 `<table>` 排版；
  - `<meta name="format-detection" …>` 加上 `x-apple-data-detectors` 样式：不然 iOS 会把金额、日期、卡号识别成蓝色链接；
  - 声明 `color-scheme`：不然深色模式下 iOS 会自动反色；
  - 隐藏的预览文字：邮件列表里主题下面显示"本月合计应还 ¥… · 3 张卡 · 消费 ¥…"。
  - **JavaScript 在任何邮件客户端都不会执行**，所以没有交互式图表；外部图片也一概不引（会暴露打开邮件的时间和 IP，断网还会白板）。
- emoji 只选不需要"变体选择符"（U+FE0F，不可见字符）的，有测试检查。
- **不放任何链接，不引用外部字体或图片**。邮件另附纯文本版本。
- **本地预览**：`autobill preview-email [--cycle 2026-09] [-o 文件]` 把这个月的邮件写成 HTML，不发信。检查排版用 WebKit 内核（和 iOS 同一个内核）在 375 像素宽下看浅色、深色两种，并点开折叠看一次。

## 提醒邮件
实现在 `autobill/notify/alerts.py`（M8b）。放到服务器上自动运行以后，没人看命令行输出，所以需要作者动手的事都发一封提醒邮件到同一个 iCloud 收件箱：

| 提醒 | 什么时候 | 邮件里说什么 |
|---|---|---|
| **收到一封不认识的邮件** | 发给别名的邮件，哪家解析器都不认识 | 主题和发件人；如果是新银行的账单，把它发给开发者加解析器，之后 `run --rescan` 补上；银行的验证码、通知可以忽略 |
| **账单解析失败** | 认出了银行，但格式对不上（`FAILED`） | 银行、主题、原因；银行可能改了格式，修好后 `run --rescan` 补上 |
| **发现新卡** | 出现一个数据库里从没有过的账户 | 新办的卡不用管；换卡的话在 `cards.card_aliases` 里接上旧账户。**第一次导入时不提醒**（那时每张卡都是"新"的） |
| **收不到账单：登录邮箱失败** | IMAP 登录失败 | 原因；改过 Apple ID 密码的话，App 专用密码会失效，重新生成并填进服务器的 `~/.config/autobill.env` |

- **同一个问题只提醒一次**：提醒存在 `alerts` 表里，按（类型，对象）去重，发出去就不再发；每 30 分钟运行一次也不会刷屏。
- **登录失败的提醒在下一次登录成功后清掉**，以后再失败会重新提醒。
- 一次运行里的所有新提醒合成**一封**邮件，标题是 `⚠ AutoBill 提醒：<第一条> 等 N 条`，版式和进度邮件同一套（iOS 分组列表、深色模式）。
- `run --no-send` 时提醒先存着，下一次正常运行一起发。
- 提醒邮件也带 `X-AutoBill-Report` 头，永远不会被当成账单读回来。
- **发不出提醒的一种情况**：收信和发信用同一个 App 专用密码，而它失效了。这时只能从服务器日志或者"进度邮件不来了"发现。

## 通道：邮件（第一版）
- 作者的配置：用 iCloud 的 `smtp.mail.me.com`，**587 端口 + STARTTLS**（`security: starttls`），**从自己的 iCloud 主地址发给自己**（`to_addr`，2026-09-19 定）。附件里的标准账单 PDF 也就存进了 iCloud。
  - QQ、163 这类用 465 端口 + SSL（`security: ssl`，默认值）。
- 配置在 `config.yaml` 的 `notifier.smtp_report`（`enabled` 默认 `false`）；密码只从环境变量读：`AUTOBILL_SMTP_PASSWORD`，没设时用 `AUTOBILL_IMAP_PASSWORD`（iCloud 收发同一个密码），见 [security.md](security.md#密钥)。
- 邮件头带 `X-AutoBill-Report: true`，作为"不会把自己的报表当账单解析"的第二道防线。
- **告警也走邮件**：解析失败（附上原邮件的主题和日期）、UNRECOGNIZED、运行中出错。

## 以后：企业微信
- 调用腾讯官方接口 `qyapi.weixin.qq.com/cgi-bin/message/send`，通过"微信插件"推送到个人微信，只经过腾讯的服务器。

## 以后：企业微信中转与看门狗
**数据留在家里，Oracle 只做两件事。**
- 家里电脑通过 WireGuard 把**摘要字段**发给 Oracle 上的中转服务；中转服务再用固定公网 IP 调用 `qyapi`。可信 IP 配成 Oracle 的固定 IP，用回调 URL 完成验证。
- 中转服务的两件事：
  1. **转发摘要**：只接收白名单里的字段，**不存储**。
  2. **心跳看门狗**：家里电脑每次运行都 ping 它一次；超过 N 小时没收到，就通过企业微信告警"AutoBill 已停止运行"。
- 邮箱授权码、流水、数据库，始终不出家门。
