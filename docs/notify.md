# 报表与推送

对应代码：`autobill/report/`（聚合、图表、模板）、`autobill/notify/`（`mail.py`；以后加 `wecom.py`），以后还有独立的小服务 `relay/`。

**原则：报表只做汇总和可视化，不列逐笔流水。** 明细去看银行的原账单。**不做还款提醒**，只展示还款日。

## 统计口径
- **每笔流水**都保留原币种金额（例如澳元消费记为"39.90 AUD，入账 28.25 USD"）。
- **支出合计**：按账单上写的各币种**入账金额**分别相加，再按汇率折算成人民币合计。汇率规则见 [data-model.md](data-model.md#汇率)，报表里注明"按 YYYY-MM-DD 汇率折算"。
- **哪些算支出**：

  | 类型 | 是否算支出 |
  |---|---|
  | `PURCHASE`、`FEE`、`INTEREST`（含分期利息）、`CASH` | 算 |
  | `REFUND`、`REBATE` | 从支出里扣减 |
  | `INSTALLMENT`（分期本金） | **不算**。以农行"总账分期"为例，这笔钱当初消费时已经算过一次，现在只是分期还回去，再算就重复了 |
  | `REPAYMENT`、`FX_TRANSFER`、合成调整 | 不算 |

- **月度归属**：按**交易日所在的自然月**归属，不按账单周期（各行账单日不同）。

### 分类规则
实现在 `autobill/categorize.py`（M6）。

- **规则文件**：`<数据目录>/rules.yaml`，也可以用环境变量 `AUTOBILL_RULES` 指到别处；`rules.yaml` 不入库。**没有这个文件时用内置默认规则**，内容和仓库里的 [`rules.example.yaml`](../rules.example.yaml) 完全相同（有测试保证两份一致）。写了自己的 `rules.yaml` 后，它**整个替换**默认规则，不是合并。
- **格式**：`分类: [关键词, 关键词, …]`。
- **怎么匹配**：拿每笔消费的**原始描述**（`description_raw`）去匹配关键词，**不分大小写**，从上往下，**第一个匹配上的分类生效**。所以具体的规则要放在前面，"微信/支付宝（未细分）"放在最后。
  - 早先的设计是"先清洗商户名再匹配"。实现时改成了直接匹配原始描述：清洗会去掉"财付通""支付宝-"这些渠道前缀，"微信/支付宝（未细分）"就永远匹配不上了。
- **手续费、利息、取现**不走规则，按交易类型直接归为"手续费""利息""取现"。
- **分类在出报表时现算，不存进数据库**：改了 `rules.yaml`，下一次看报表就生效，不用重新导入。
- 默认规则只放连锁品牌（超市、交通、餐饮、订阅等），独立小店留给你自己加：

  ```yaml
  超市: [Woolworths, WW METRO, Coles, IGA, UMALL, Everyday Extra, FRANPRIX]
  交通: [TFNSW OPAL, "UBER *TRIP", Suica]
  餐饮: [KFC, MCDONALDS, STARBUCKS, "UBER * EATS", HungryPanda]
  住宿: [AIRBNB]
  订阅: [APPLE.COM/BILL, SPOTIFY]
  通讯网络: [SUPERLOOP, OPTUS]
  水电燃气: [ORIGIN ENERGY]
  健身: [PlusFitness]
  娱乐: [GREATER UNION, EVENT CINEMAS, DISNEY]
  网购: [TEMU, AMAZON]
  微信/支付宝（未细分）: [财付通, 支付宝, 微信]
  ```

- **已知限制**：国内用微信、支付宝付款的消费，账单上只写"财付通，深圳市腾讯计算机系统有限公司"或"支付宝-…"，**看不到真正的商户**。这是银行账单本身的信息不够，不是程序出错。这类消费统一归到"微信/支付宝（未细分）"。
- 没匹配上的商户会在报表里列出来（"未分类的商户"），方便你往 `rules.yaml` 里补规则。

## 报表什么时候发
**没有定时月报。每收到一份账单，就发一封邮件**，内容包括：
1. 这份账单的摘要；
2. 这份账单涉及月份的**最新汇总**。

- 一份账单通常跨两个自然月，比如 8/17 到 9/16，所以涉及的 8 月和 9 月都会重新计算。
- 某个月份还有别的卡的账单没到时，汇总里注明"本月数据未完整：还缺 X 行 XXXX 卡"。
  - 按样本推算，某个月要到下个月 24 日左右，所有卡的账单才会到齐。
  - 到齐后的那封邮件，就是这个月完整的汇总。
- 想随时查看某个月，可以在终端运行 `autobill report --month YYYY-MM`。
  - **M3 的终端版**只有最基本的内容：每张卡、每份账单、每个币种一行支出合计，以及所用汇率（日期、来源）和折算后的人民币；最后是分币种合计和人民币合计。对账有警告、未对账、用了配置汇率、取不到汇率的行都会标出来。
  - **M6 起**又加了五节，都是汇总，不列逐笔：
    1. **分类**：各分类的人民币金额和占比，只统计消费；返现、退款单独一行"（扣减）"；
    2. **按卡**：每张卡当月的人民币支出；
    3. **近 6 个月**：每月人民币合计，没有数据的月份显示"没有数据"；
    4. **支出最多的商户**：前 10 名，商户加金额；
    5. **未分类的商户**：按金额排的前 10 个，带笔数，提示补 `rules.yaml`。
  - 每笔金额都按它所属账单的汇率折算；各项分别四舍五入，和合计可能差几分钱。
  - "还缺哪些卡""还款日一览"和图表放在 M7 的邮件报表里。

## 邮件内容
**按手机屏幕设计**，单栏排版，从上到下：

**第一部分：本期账单摘要**
- 银行、卡号后四位、账单日、**还款日**；
- 各币种的应还金额，以及折算成人民币的合计；
- 本期支出合计（人民币），附各币种原值；
- 支出最多的 3 个分类；
- 状态标记：`UNVERIFIED` 显示"未对账"。

**第二部分：涉及月份的汇总**（每个月一节）
1. 本月总支出（人民币）、各币种原值、所用汇率和日期、是否已完整；
2. 分类占比（环形图）；
3. 按卡分布（条形图）；
4. 近 6 个月趋势（折线图）；
5. 支出最多的商户 Top 10（只显示商户和金额，不列逐笔）；
6. 返现、退款合计；
7. 未分类商户 Top N；
8. 各卡还款日一览（只列日期和金额，不是提醒）。

**实现（M7）**：`autobill/report/mail_report.py` + 模板 `report/templates/bill_report.mjml.j2`。

- **排版用 [MJML](https://mjml.io/)**（Python 版 mjml-python，MIT）：它把模板转成邮件客户端认得的表格布局和内联样式，手机上自动单栏。
- **所有"图表"都是 HTML 横条，不用图片**（2026-09-19 作者选定，替换了最初的 matplotlib 方案）。原因：QQ 邮箱、网易邮箱默认不显示图片，报表必须在不点"显示图片"时也完整。环形图、折线图因此不做；参考 Copilot Money、Monzo、支付宝月账单的做法，用排名横条代替。
- **设计规则**：
  - 每节开头一个大数字（本月所有卡合计），下面是"比上个月多/少 x%"；**这个月还缺卡时不做环比**，避免拿半个月和整月比。
  - 一个主色（蓝 `#2a78d6`，来自验证过的配色）表示重点，灰色表示参照；文字永远是黑/灰，不用系列颜色。
  - 分类：前 5 名单列，其余合并成"其他"；"未分类"放最后、用灰色（它是待补的规则，不是一种支出）；占比很小时写"<1%"，不写"0%"。
  - 近 6 个月：本月主色，其他月份灰色，没有数据的月份写"没有数据"。
  - "本月未完整"是浅橙底色的提示框，带 ⚠ 图标，不只靠颜色。
- **还缺哪些卡**：最近约两个月出过账单的卡算"应有"；某月的"下一期账单"（账单日在月底之后 45 天内、并且周期覆盖到月底）还没到，就算缺。更晚的账单不算，免得漏掉中间缺的月份。
- **各卡还款日**：只列金额、账单日和"x 月 x 日前还款"，不是提醒。
- 同一份 HTML 也能写成本地预览文件：`autobill preview-email`。
- 邮件另附纯文本版本（给不显示 HTML 的客户端）。**不放任何链接，不引用外部字体或图片。**

## 通道：邮件（第一版）
- 用 `smtplib.SMTP_SSL`，端口 465，从中心邮箱发到主邮箱。原始账单本来就在主邮箱里，所以不会让数据多暴露给任何一方。
- 配置在 `config.yaml` 的 `notifier.smtp_report`（`enabled` 默认 `false`）；授权码只从环境变量 `AUTOBILL_SMTP_PASSWORD` 读，见 [security.md](security.md#密钥)。
- 邮件头带 `X-AutoBill-Report: true`，作为"不会把自己的报表当账单解析"的第二道防线。
- **告警也走邮件**：解析失败（附上原邮件的主题和日期）、UNRECOGNIZED、运行中出错。

## 以后：企业微信
- 调用腾讯官方接口 `qyapi.weixin.qq.com/cgi-bin/message/send`，通过"微信插件"推送到个人微信，只经过腾讯的服务器。
- **只推第一部分的摘要**。不推图表和明细，因为企业微信不是端到端加密的。
- **只推本人**：`touser` 填本人的 userid，不用 `@all`；应用的可见范围也只勾本人。
- **可信 IP 门槛**：2022-06 之后新建的自建应用，必须配置企业可信 IP 才能调用接口（否则报 60020）。配置可信 IP 之前，要先配可信域名（需备案且主体一致）或"接收消息服务器 URL"。

## 以后：企业微信中转与看门狗
**数据留在家里，Oracle 只做两件事。**
- 家里电脑通过 WireGuard 把**摘要字段**发给 Oracle 上的中转服务；中转服务再用固定公网 IP 调用 `qyapi`。可信 IP 配成 Oracle 的固定 IP，用回调 URL 完成验证。
- 中转服务的两件事：
  1. **转发摘要**：只接收白名单里的字段，**不存储**。
  2. **心跳看门狗**：家里电脑每次运行都 ping 它一次；超过 N 小时没收到，就通过企业微信告警"AutoBill 已停止运行"。
- 邮箱授权码、流水、数据库，始终不出家门。
