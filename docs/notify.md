# 报表与推送

对应代码：`autobill/report/`（聚合、图表、模板）、`autobill/notify/`（`mail.py`；以后加 `wecom.py`），以后还有独立的小服务 `relay/`。

**原则：邮件第一眼只看到汇总和可视化；逐笔流水折叠在邮件里（默认收起，轻点展开），完整的[标准账单](statement.md)作为 PDF 附件。** **不做还款提醒**，只展示还款日。

## 统计口径
- **每笔流水**都保留原币种金额（例如澳元消费记为"39.90 AUD，入账 28.25 USD"）。
- **支出合计**：按账单上写的各币种**入账金额**分别相加，再按汇率折算成人民币合计。汇率规则见 [data-model.md](data-model.md#汇率)，报表里注明"按 YYYY-MM-DD 汇率折算"。
- **哪些算支出**：

  | 类型 | 是否算支出 |
  |---|---|
  | `PURCHASE`、`FEE`、`INTEREST`（含分期利息）、`CASH` | 算 |
  | `REFUND`、`REBATE` | 从支出里扣减 |
  | `INSTALLMENT`（分期本金） | **不算**。以农行"总账分期"为例，这笔钱当初消费时已经算过一次，现在只是分期还回去，再算就重复了 |
  | `REPAYMENT`、`FX_TRANSFER`、合成调整 | 不算 |

- **月度归属**：按**交易日所在的自然月**归属，不按账单周期（各行账单日不同）。

### 分类规则
实现在 `autobill/categorize.py`（M6；M7d 加了整词匹配、商户名匹配和行业通用词）。

- **规则文件**：`<数据目录>/rules.yaml`，也可以用环境变量 `AUTOBILL_RULES` 指到别处；`rules.yaml` 不入库。**没有这个文件时用内置默认规则**，内容和仓库里的 [`rules.example.yaml`](../rules.example.yaml) 完全相同（有测试保证两份一致）。写了自己的 `rules.yaml` 后，它**整个替换**默认规则，不是合并。
- **格式**：`分类: [关键词, 关键词, …]`。关键词有两种：
  - `Woolworths`：描述里任何位置出现就算。连锁品牌名用这种。
  - `word:BAR`：只算完整的单词。匹配 `LS BAR PLANET`，不匹配 `BARBER`；`word:MARKET` 不会误中 `AMAZON MARKETPLACE`。短的通用词用这种。字母和数字算单词的一部分，空格、`*`、`_`、`.` 这些都算分隔。
- **怎么匹配**：拿每笔消费的**原始描述**（`description_raw`）**和解析器拆出来的商户名**一起去匹配，**不分大小写**，分类从上往下，**第一个匹配上的分类生效**。所以具体的规则要放在前面，"微信/支付宝（未细分）"放在最后。
  - 商户名一起匹配（M7d）：中行把国家代码粘在店名后面（`SUKIYAJPN`），解析器早就把它拆成商户 `SUKIYA` 和地点 `JPN`，但原来只拿原始描述匹配，整词规则对不上。
  - 早先的设计是"先清洗商户名再匹配"。实现时改成了直接匹配原始描述：清洗会去掉"财付通""支付宝-"这些渠道前缀，"微信/支付宝（未细分）"就永远匹配不上了。所以现在是**原始描述加商户名**一起匹配。
- **手续费、利息、取现**不走规则，按交易类型直接归为"手续费""利息""取现"。
- **分类在出报表时现算，不存进数据库**：改了 `rules.yaml`，下一次看报表就生效，不用重新导入。
- **默认规则 = 连锁品牌 + 行业通用词**（M7d）：
  - 只写连锁品牌时，样本里 181 笔消费有 86 笔是"未分类"：大多是悉尼、日本、欧洲的独立小店，每家只出现一两次，按店名写规则永远写不完。
  - 于是每个分类再加上"行业通用词"（`KITCHEN`、`GRILL`、`BUFFET`、`NOODLE`、`word:CAFE`、`word:BAR`、`SUPERMARKET`、`word:MARKET`、`CONVENIENCE`、`AIRPORT`、`STAZIONE`、`TOBACCO`、`CELLARS`……），新加了"烟酒"分类。样本里的未分类从 86 笔降到 37 笔。
  - 每条新词都拿样本逐个核对过；**有歧义的词不放**：`BUTCHER`（"Butchers Buffet"是餐厅）、`METRO`（既可能是地铁也可能是店名）、`HOTEL`（澳洲的 Hotel 大多是酒吧）。宁可留在"未分类"让你补，也不要悄悄分错。
  - 完整内容见 [`rules.example.yaml`](../rules.example.yaml)。
- **已知限制**：国内用微信、支付宝付款的消费，账单上只写"财付通，深圳市腾讯计算机系统有限公司"或"支付宝-…"，**看不到真正的商户**。这是银行账单本身的信息不够，不是程序出错。这类消费统一归到"微信/支付宝（未细分）"。
- **为什么不用 MCC（商户类别码）**：MCC 在刷卡授权时就有，但三家银行的电子账单都不打印它（7 份样本全部解码检查过，也没有"商户类别""商户编号"）。按店名反查 MCC 没有免费、可靠的数据库，Visa、Mastercard 的查询接口只对企业开放；而且微信、支付宝付款的 MCC 是支付平台自己的，拿到也分不出真正的店。
- **补规则**：`autobill uncategorised [--cycle 2026-09] [--limit 20] [--suggest]` 按人民币金额列出还没分类的商户（笔数、金额），并生成一段可以直接复制进 `rules.yaml` 的 YAML。你常去的店是固定的，每家只需要补一次。进度邮件的分类卡片下面有"未分类"时也会提示这个命令。

### 分类建议与 AI 接口
**原则：解析和金额永远不用 AI**（钱数必须确定、可复查）；**分类这类"建议"可以接 AI**（2026-09-19 作者确认：项目要给以后接 AI 预留接口）。

- 实现在 `autobill/suggest.py`（M7d 只留接口，还没有接任何 AI）：
  - `CategorySuggester` 协议：输入商户名列表和分类名列表，返回"商户 → 分类"；
  - `register(名字, 工厂函数)` 注册提供方；`config.yaml` 的 `ai.provider`（和 `ai.model`、`ai.base_url`）选用哪一个；密钥只从环境变量 `AUTOBILL_AI_API_KEY` 读；
  - 以后接本机的 Ollama（qwen 等）或者兼容 OpenAI 的接口，只要写一个提供方并注册，不用改别处。
- `autobill uncategorised --suggest` 调用它：建议按分类分组，标注"AI 建议，确认后再用"，**只打印，从不自动写进 `rules.yaml`**。所以报表始终由规则决定，结果可复现。
- **只发出商户名和分类名**：金额、日期、卡号和账单里的其他内容都不会交给 AI（有测试检查）。AI 编出来的商户或不存在的分类会被丢掉。
- 没配置 `ai.provider` 时，`--suggest` 只提示一句，照常列出未分类的商户。

## 账单月进度邮件
**没有定时月报。每次运行导入了新账单，就按"账单月"发邮件**（M7c，2026-09-19 作者和 Gemini 讨论后确定，替换了 M7 的"每份账单一封、按涉及月份汇总"）。

- **账单月 = 出账日所在的月份**，和银行的叫法一致（银行的"2026年09月账单"就是 9 月出账的那一期）。每张卡每月出账一次，所以一个账单月里每张卡最多一份。
- **卡包**：`config.yaml` 的 `cards.portfolio` 列出每月应该出账的卡和大约的账单日（见 [config.example.yaml](../config.example.yaml)）。
  - 不配置时，最近约两个月出过账单的卡算"应有"，账单日取它最近一期的日子。
  - 配了卡包也不会把"那时还没开卡"的卡算进过去的月份：某张卡的第一份账单比这个月还晚，就不列。
- **每张卡的状态**：
  - **已出账**：这个月有它的账单，显示应还（折合人民币）、出账日、还款日；
  - **待出账**：还没到，而且没超过通常账单日 7 天；
  - **可能无账单**：超过通常账单日 7 天还没到。有的银行在没有消费的月份不出账单，这样就不会一直卡在 5/6。
- **什么时候发**：
  - 同一次运行里同一个账单月到了几份账单（例如农行 3 张卡同一天出账），**只发一封**；不同账单月各发一封，从早到晚。
  - 没有卡"待出账"时，这封就是这个月的**最后一封（已齐）**。
  - 某个月还在等卡，而之后的运行里剩下的卡都超时成了"可能无账单"，没有新账单也会补发一封"已齐"。已经齐了的月份不再发。
- **邮件折叠成一个对话**：同一账单月的邮件用同一个主题 `📊 2026年9月 信用卡账单`，第二封起带 `In-Reply-To` / `References` 指向之前的邮件（记在 `cycle_threads` 表里）。Apple 邮件按这两个邮件头把它们折叠在一起，比只靠主题相同可靠。
- 想随时查看某个自然月的汇总，可以在终端运行 `autobill report --month YYYY-MM`（按交易日归属，见上面的统计口径）：
  - 每张卡、每份账单、每个币种一行支出合计，以及所用汇率和折算后的人民币；
  - 分类（返现、退款单独一行"扣减"）、按卡、近 6 个月、支出最多的商户、未分类的商户；
  - 每笔金额按它所属账单的汇率折算；各项分别四舍五入，和合计可能差几分钱。

## 邮件内容
**只为 iPhone 上的苹果邮件（iCloud 邮箱）排版，目标是 iOS 原生 App 的质感**（2026-09-19 作者要求：完全抛弃财务报表的表格感）。

**设计参考**：
- **Apple 自己的设计语言**（Human Interface Guidelines）：大标题、分组圆角列表和缩进的细分隔线（设置、钱包）、系统配色（分组背景 `#F2F2F7`，深色是纯黑 + `#1C1C1E`）、`-apple-system` 字体和 SF Pro Rounded 大数字；
- **健身 App 的活动圆环**：进度圆环，每张卡一段；
- **钱包 App**：卡片缩略图（深灰渐变，只有银行首字和尾号，不仿冒银行卡面）；
- **日历 App**：还款日用日历图标式的日期块；
- **屏幕使用时间**：每日消费柱状图加一条虚线表示日均；
- **Apple Card、Copilot Money**：金额的"大整数、小分位"写法；每个分类一个 emoji 图块；所有分类合成一根分段胶囊条；跨卡的"花得最多的商户"。

**第一眼只看到汇总**，长列表都折叠起来（交互克制）。从上到下：

1. **大标题** `2026年9月`，下面一行状态：`还有 2 张待出账，1 张可能无账单` / `✓ 本月账单已齐`。
2. **汇总卡片**：进度圆环（已出账是主色、待出账是灰色、可能无账单是半透明橙色，中间写 `3/6`）+ "已出账合计应还"（折合人民币）+ 图例。
3. **卡片**：分组列表，每张卡一行：钱包式缩略图、银行和尾号（新到的带"新"标记）、出账日和还款日，右边是应还和状态（✓ 已出账 / 时钟 待出账 / ! 可能无账单，图标加文字，不只靠颜色）。
4. **本月消费**：已出账各卡合计（已扣返现和退款）、一根分段胶囊条、每个分类一行（emoji 图块、颜色标记、占比、金额）。
   - 颜色：前 4 个分类用验证过的分类色（第 1–4 号），其余合并成"其他"（灰色），"未分类"放最后（灰色斜纹）。这一组颜色用 dataviz 的校验脚本在浅色、深色两种背景下都跑过（相邻色块色弱可分）；超过 4 类再加颜色就过不了。
   - "花得最多的商户"（所有已出账的卡，前 5 名）默认**折叠**，轻点展开。
5. **每份新账单**：本期应还、本期消费、每日消费柱状图（虚线是日均）、这份账单最多的 3 个分类（颜色和上面的分类条一致）。
   - **全部逐笔流水**默认**折叠**，轻点展开（按日期分组；每笔有 emoji 图块、商户、分类和原币等小字、金额；返现、退款显示成绿色的 `+`；还款、分期本金、购汇、调整标"不计入支出"）。
   - **默认不附 PDF**（2026-09-19 作者决定：原始账单直接在邮箱里看，进度邮件不再附 PDF）。想附的话在 `config.yaml` 写 `statement: {email_pdf: true}`，而且运行的机器上要有 Edge 或 Chrome（Docker 镜像里没有）；附上时这里多一行附件说明。
6. **这个月已齐时**再加"还款日"：日历式日期块，按日期排序，只列事实，不是提醒。
7. 页脚：汇率说明、"金额以银行原账单为准"、生成时间。

**实现（M7c）**：`autobill/report/cycle.py` + 模板 `report/templates/cycle_report.html.j2`；共用的配色、emoji 在 `report/style.py`。

- **折叠用 CSS 的"复选框技巧"**（checkbox hack），不用脚本：一个隐藏的 `<input type="checkbox">`，点它的 `<label>` 切换选中状态，CSS 用 `:checked` 显示或隐藏后面的内容。苹果邮件（iOS 和 macOS）支持；不支持的客户端里内容保持折叠。
- **苹果邮件的处理**：
  - `<style>`、CSS 变量、`prefers-color-scheme` 深色模式、内嵌 SVG 都能用，所以不用 MJML 的表格排版，也没有 `<table>`；
  - `<meta name="format-detection" …>` 加上 `x-apple-data-detectors` 样式：不然 iOS 会把金额、日期、卡号识别成蓝色链接；
  - 声明 `color-scheme`：不然深色模式下 iOS 会自动反色；
  - 隐藏的预览文字：邮件列表里主题下面显示"已出账 3/6 · 合计应还 ¥… · 还有 2 张待出账"。
- emoji 只选不需要"变体选择符"（U+FE0F，不可见字符）的，有测试检查。
- **不放任何链接，不引用外部字体或图片**。邮件另附纯文本版本。
- **本地预览**：`autobill preview-email [--cycle 2026-09] [-o 文件]` 把这个月下一封邮件写成 HTML，不发信。检查排版用 WebKit 内核（和 iOS 同一个内核）在 390 像素宽下看浅色、深色两种，并点开折叠看一次。

## 提醒邮件
实现在 `autobill/notify/alerts.py`（M8b）。放到服务器上自动运行以后，没人看命令行输出，所以需要作者动手的事都发一封提醒邮件到同一个 iCloud 收件箱：

| 提醒 | 什么时候 | 邮件里说什么 |
|---|---|---|
| **收到一封不认识的邮件** | 发给别名的邮件，哪家解析器都不认识 | 主题和发件人；如果是新银行的账单，把它发给开发者加解析器，之后 `run --rescan` 补上；银行的验证码、通知可以忽略 |
| **账单解析失败** | 认出了银行，但格式对不上（`FAILED`） | 银行、主题、原因；银行可能改了格式，修好后 `run --rescan` 补上 |
| **发现新卡** | 出现一个数据库里从没有过的账户 | 新办的卡不用管；换卡的话在 `cards.card_aliases` 里接上旧账户。**第一次导入时不提醒**（那时每张卡都是"新"的） |
| **收不到账单：登录邮箱失败** | IMAP 登录失败 | 原因；改过 Apple ID 密码的话，App 专用密码会失效，重新生成并填进服务器的 `~/.config/autobill.env` |

- **同一个问题只提醒一次**：提醒存在 `alerts` 表里，按（类型，对象）去重，发出去就不再发；每 30 分钟运行一次也不会刷屏。
- **登录失败的提醒在下一次登录成功后清掉**，以后再失败会重新提醒。
- 一次运行里的所有新提醒合成**一封**邮件，标题是 `⚠ AutoBill 提醒：<第一条> 等 N 条`，版式和进度邮件同一套（iOS 分组列表、深色模式）。
- `run --no-send` 时提醒先存着，下一次正常运行一起发。
- 提醒邮件也带 `X-AutoBill-Report` 头，永远不会被当成账单读回来。
- **发不出提醒的一种情况**：收信和发信用同一个 App 专用密码，而它失效了。这时只能从服务器日志或者"进度邮件不来了"发现。

## 通道：邮件（第一版）
- 作者的配置：用 iCloud 的 `smtp.mail.me.com`，**587 端口 + STARTTLS**（`security: starttls`），**从自己的 iCloud 主地址发给自己**（`to_addr`，2026-09-19 定）。附件里的标准账单 PDF 也就存进了 iCloud。
  - QQ、163 这类用 465 端口 + SSL（`security: ssl`，默认值）。
- 配置在 `config.yaml` 的 `notifier.smtp_report`（`enabled` 默认 `false`）；密码只从环境变量读：`AUTOBILL_SMTP_PASSWORD`，没设时用 `AUTOBILL_IMAP_PASSWORD`（iCloud 收发同一个密码），见 [security.md](security.md#密钥)。
- 邮件头带 `X-AutoBill-Report: true`，作为"不会把自己的报表当账单解析"的第二道防线。
- **告警也走邮件**：解析失败（附上原邮件的主题和日期）、UNRECOGNIZED、运行中出错。

## 以后：企业微信
- 调用腾讯官方接口 `qyapi.weixin.qq.com/cgi-bin/message/send`，通过"微信插件"推送到个人微信，只经过腾讯的服务器。
- **只推第一部分的摘要**。不推图表和明细，因为企业微信不是端到端加密的。
- **只推本人**：`touser` 填本人的 userid，不用 `@all`；应用的可见范围也只勾本人。
- **可信 IP 门槛**：2022-06 之后新建的自建应用，必须配置企业可信 IP 才能调用接口（否则报 60020）。配置可信 IP 之前，要先配可信域名（需备案且主体一致）或"接收消息服务器 URL"。

## 以后：企业微信中转与看门狗
**数据留在家里，Oracle 只做两件事。**
- 家里电脑通过 WireGuard 把**摘要字段**发给 Oracle 上的中转服务；中转服务再用固定公网 IP 调用 `qyapi`。可信 IP 配成 Oracle 的固定 IP，用回调 URL 完成验证。
- 中转服务的两件事：
  1. **转发摘要**：只接收白名单里的字段，**不存储**。
  2. **心跳看门狗**：家里电脑每次运行都 ping 它一次；超过 N 小时没收到，就通过企业微信告警"AutoBill 已停止运行"。
- 邮箱授权码、流水、数据库，始终不出家门。
