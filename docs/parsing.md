# 解析框架

对应代码：`autobill/parse/`，包含 `base.py`、`registry.py`、`util.py`、`abc.py`、`ccb.py`、`boc.py`、`heuristic.py`。各银行的格式规格见 [banks/](banks/README.md)。**纯规则解析，不接入 AI。**

## 接口

```python
class BaseParser(ABC):
    bank: str  # "ABC" / "CCB" / "BOC"
    name: str  # "abc_html"
    version: int  # 模板改版后 +1

    @abstractmethod
    def matches(self, msg: RawMessage) -> bool: ...

    @abstractmethod
    def parse(self, msg: RawMessage) -> list[Bill]:
        """一封邮件可能拆出多份账单（中行合并账单里可能有多张卡），所以返回列表。
        找不到关键区块或字段时抛 TemplateChanged，绝不返回空列表。"""
```

- 接口在 `autobill/parse/base.py`（M2），`TemplateChanged` 也定义在这里。
- **`parse()` 返回的账单已经对过账**：解析器最后一步调用 `reconcile()`，所以出来的 `Bill` 一定带着最终的 `status`、`warnings` 和合成流水。

**分派流程**（M3 起）：
1. 用注册表（[banks/README.md](banks/README.md)）识别出是哪家银行；
2. 这家银行的解析器按版本从新到旧依次尝试，取第一个通过校验的；
3. 全部失败时：第一版直接标为 FAILED 并告警；以后交给兜底解析器。

## 三种版面，三种定位方法
三家的结构完全不同，但有一条共同规则：**用中文区块标题定位，不用位置下标，也不用英文表头。**

| 银行 | 版面 | 定位方法 |
|---|---|---|
| 农行 | 约 37 张没有 id/class 的叶子表**按顺序排列** | **顺序状态机**：遍历叶子表，遇到 `账务说明`、`交易明细`、`分期记录` 等标题就切换区块；遇到分组行 `['', '●', 名称]` 就切换分组 |
| 建行 | 容器表嵌套子表 | **锚点查找**：按 `龙卡信用卡对账单`、`信用信息`、`应还款信息`、`【交易明细】` 找到子表；明细表里再按"账户分节行"和"8 格交易行"区分 |
| 中行 | PDF | **标签加坐标**：先用 `dedupe_chars()` 去掉伪粗体造成的重复字符，再按中文标签（`账单日`、`到期还款日`、`账号类型`、`卡号：`）定位，用 `extract_words()` 的坐标取对应的值 |

## 健壮性规则

### 终态
每封邮件都必须落到一个终态：`OK / WARN / UNVERIFIED / FAILED / UNRECOGNIZED / IGNORED`，不存在"没有结果"。
- `UNRECOGNIZED`：邮件看起来像账单（主题里有"账单/对账单"），但没有解析器认领。会告警，提示要补解析器。

### 找不到就报错
- 找不到区块标题或表头时抛 `TemplateChanged`。
- 空流水只有在"本期新增 = 0 且本期还款 = 0"时才合法。
- 单行解析失败的写进 `Bill.warnings`（附上这一行的原文），账单标为 `WARN`，不中断整份账单。

### 不变量
- 必填字段：账单日、各币种的应还金额。
- 还款日只有在应还金额为 0 时才允许为空（中行实测会出现），不为空时要落在账单日之后的合理天数内（按银行配置）。
- 对账必须通过，见 [data-model.md](data-model.md#对账)。

### 多版本
解析器按版本从新到旧依次尝试，账单上记录 `parser_name/parser_version`。只回填 12 个月，预计每家银行只需要一个版本。

### 兜底解析器
> **以后再做**。第一版里，解析失败就标为 FAILED，并发告警邮件，附上原邮件的主题和日期，让你自己去看原账单。

`SummaryHeuristicParser` 用"关键词就近 + 金额提取"，至少抽出应还金额和还款日，让这份账单的推送不至于整个缺失。
- 兜底结果一律标注"**未核实，请以原邮件为准**"，附上原邮件的主题和日期，`quality = 1`。
- 兜底很容易把"最低还款额"或"信用额度"误认成应还金额，所以绝不能不加标注地展示。

### 缺账单心跳
> **以后再做**。第一版不检查缺账单；报表里的"本月数据未完整：还缺 X 行"会起到类似的提示作用。

每张卡记录自己的账单日，超过账单日 N 天没收到账单就告警。转发失效、授权码过期、银行改成只在 App 发账单，这类问题只能靠这个发现。
- **按银行配置零账单行为**：中行实测在零欠款时仍然发账单；农行、建行未知。未知的银行，在"上期欠款为 0"时只记录、不告警。
- **卡号别名** `cards.card_aliases`（M8a 之后实现）：`"CCB:0009": "CCB:0004"` 这样写，账单入库前把账户号换成右边那个。两种情况用得上：
  - 换卡后尾号变了；
  - **同一账户有两张卡**，账单里两个卡号各记各的流水（作者建行 2025-06 账单：一张走银联/支付宝，一张走 Visa/Mastercard，共用一个余额）。建行解析器遇到多个卡号时取第一个并告警；配置里把它们都指向同一个账户后，这条告警就去掉，只剩这条告警的账单恢复为 OK。
  - 已经入库的账单不会自动改：本地测试数据可以删掉数据库重新导入（原始邮件都在 iCloud 里）。
- 建行在没有流水的月份拿不到卡号，见 [banks/ccb.md](banks/ccb.md)。

### 可重跑
原始邮件永久保存。解析器修好后用 `autobill reparse --bank ABC --since 2025-10` 重新解析。

## 通用工具
`autobill/parse/util.py`（M1），三家都要用。**识别不了的格式一律抛错**（`AmountError`、`CurrencyError`、`DateError`，都继承 `FormatError`），不猜。

| 函数 | 用途 |
|---|---|
| `normalize_ws()` | 空白规范化 |
| `parse_amount()` | 单个金额，符号按原样返回（`CR` 后缀视为负数）；转换成我们的符号约定是解析器的事 |
| `parse_amount_currency()` | 农行 `-28.25/USD` |
| `parse_currency_amount()` | `AUD 0.00`、`CNY 0.00` |
| `parse_directed_amount()` | 中行 `存款/CRED 0.07` → 金额 + 方向；中英文标签必须一致，金额不能再带正负号；不带标签的 `0.00` 当作 0 |
| `parse_currency()` | `人民币(CNY)`、`人民币 （CNY）`、`外币/AUD`、`RMB`、`美元` → ISO 代码；标签里出现两种币种就报错。认识约 50 个常见币种（含旅行常见的 CHF、KRW、THB 等），不在列表里的代码报错而不是放行，遇到新的再加 |
| `parse_date()` / `infer_year()` | 完整日期 / 只有月日时按账单周期推断年份 |
| `is_pdf()` | 按内容识别 PDF |

**"空白或 `-` 算 0"默认关闭**：解析器要显式传 `blank_is_zero=True`（建行的 `-`、中行的空单元格）。否则漏掉一个关键金额也会被当成 0，违反"找不到就报错"。

具体规则：

- **空白规范化**：`U+00A0` 不换行空格（建行用来填充）、`U+3000` 全角空格、`U+FEFF` BOM（农行正文里有）先转成普通空格，再合并连续空白。**例外**：农行定宽描述要在规范化**之前**按位置切分。
- **金额**：
  - 千分位 `1,234.56`；
  - 负号；
  - `金额/币种`（农行，如 `-28.25/USD`）；
  - 币种和金额分两格（建行）；
  - `存款/CRED 0.07` 这类方向标签（中行）；
  - `-` 表示 0（建行）；
  - 空单元格表示 0（中行）；
  - 为接入其他银行预留：`CR` 后缀、全角数字、`¥`/`RMB` 前缀。
- **日期**：
  - `YYMMDD`（农行明细）；
  - `YYYY-MM-DD`（建行明细、中行）；
  - `YYYY/MM/DD`（周期、还款日）；
  - `YYYY年MM月DD日`（建行问候段）；
  - `YYYYMMDD`（农行分期记录）。
  - 三家都带年份。"只有月日、需要推断年份"是为接入其他银行保留的通用逻辑：按账单周期推断，跨年时要特别处理。
- **PDF 识别**：看内容开头是不是 `%PDF-`，不看文件名或 MIME 类型（中行的附件名是编码过的中文，类型是 `octet-stream`）。
- **商户清洗**：
  - 去掉渠道前缀：`境外消费`、`网上消费`、`支付宝-`、`财付通，`；
  - 农行境外消费按"23 字符名称 + 13 字符地点"切分；
  - 非拉丁字符已经被银行替换成 `?`，保留原样。

## 测试
通用的测试规范（不联网、临时数据目录、快照怎么核对）见 [development.md](development.md#6-测试规范)。本节只讲解析器相关的部分。

- **样本**：[`tests/fixtures/`](../tests/fixtures/README.md)，是脱敏后的真实账单。
- **快照**：每封样本对应一个期望输出 `tests/snapshots/<bank>/<文件名>.json`。
  - **第一次生成的快照必须人工核对**：对账三步全部通过是前提；再随便挑几笔，和样本里的原文逐字比对。
  - 之后快照一有变动，就要在代码评审里说明原因。
  - 快照平时只做比对；只有显式设置 `AUTOBILL_UPDATE_SNAPSHOTS=1` 跑 pytest 才会写入或覆盖，写完必须人工核对。
- **每个解析器至少要有这几类测试**：
  - 快照一致；
  - 对账三步全部通过；
  - 删掉关键区块标题后，必须抛出 `TemplateChanged`，不能返回空列表；
  - 符号转换正确，比如农行支出在我们这里是正数。
- **DKIM 测试**：样本经过脱敏，签名全部失效，只能用来测"验证失败"这条分支。"验证通过"要这样测：
  1. 在测试里生成一对临时 RSA 密钥；
  2. 用 `dkimpy` 给一封合成邮件签名；
  3. 验证时传入 `dnsfunc` 桩函数，直接返回测试公钥，不走真实 DNS。
- **分两步验收**（避免一直被样本卡住）：
  - **第一版（M2、M4、M5）**：用现有 5 份样本把三家的解析器写完，建行消费、中行明细这类还没有样本的部分标为"推断"；
  - **补样本（P1b）**：每家银行 ≥3 期、覆盖 [样本覆盖矩阵](banks/README.md#样本覆盖矩阵) 里的主要场景以后，再把"推断"改成"已验证"。
